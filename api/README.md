# `api/` — два серверні ендпоінти

Сайт статичний, але дві речі статикою не робляться: прийняти заявку й створити
рахунок на оплату. Для обох на Hostinger є PHP — більше там із динаміки нічого
немає.

| Файл | Що робить | Секрети |
|---|---|---|
| `lead.php` | приймає заявку з форми й розкладає її в CRM «Мій комп'ютер» і в Google-таблицю | `lead-config.php` |
| `pay.php` | створює рахунок у WayForPay або MonoPay і повертає адресу сторінки оплати | `pay-config.php` |

Обидва конфіги лежать **на рівень вище за `public_html`**:

```
/home/u260300169/domains/fluent-fox.site/lead-config.php
/home/u260300169/domains/fluent-fox.site/pay-config.php
```

Це не примха. `rsync` на викатці чистить `public_html` через `--delete`, тож
усередині жоден файл із ключами не пережив би й однієї викатки. Заодно звідти
його не віддати по HTTP.

Кладе обидва сам деплой із секретів репозиторію — руками на сервер лазити не
треба. Зразки для розуміння структури: `lead-config.sample.php`,
`pay-config.sample.php`.

## Як увімкнути оплату

Код уже на проді. Поки ключів немає, `pay.php` свідомо відповідає
`503 {"error": "Оплата на сайті тимчасово недоступна…"}` і нічого не створює,
а `/oplata` не стоїть ні в підвалі, ні в `sitemap.xml` — щоб відвідувач не
впирався в мертву кнопку.

### Крок 1. Три секрети в GitHub

**Settings → Secrets and variables → Actions → New repository secret.**

| Ім'я секрету | Звідки взяти |
|---|---|
| `WFP_MERCHANT` | кабінет WayForPay → **Налаштування → Реквізити мерчанта** → `Merchant account` |
| `WFP_SECRET` | там же → `Merchant secret key` |
| `MONO_TOKEN` | monobank Еквайринг → **Налаштування → Токен мерчанта** (`X-Token`) |

Імена мають збігатися символ у символ: саме їх читає крок «Покласти конфіг
оплати» в `.github/workflows/deploy.yml`.

Решта секретів у репозиторії вже є, і чіпати їх не треба — вони від заявок і
від самої викатки: `SFTP_HOST`, `SFTP_PORT`, `SFTP_USER`, `SFTP_PASSWORD`,
`CRM_ADMIN_TOKEN`, `CANARY_TOKEN`, `LEAD_NOTIFY_EMAIL`.

Можна покласти тільки один зі шлюзів. Якщо заданий лише `MONO_TOKEN`, кнопка
MonoPay працюватиме, а WayForPay відповість «Не вдалося створити рахунок» —
причина (`wfp_merchant або wfp_secret не задані`) ляже в `pay-errors.log`.
Сам крок деплою мовчки пропускає себе лише тоді, коли немає **обох**.

### Крок 2. Дозволити домен у кабінеті WayForPay

Це найлегше пропустити, і саме на цьому все стане. WayForPay підписує запит
**разом із доменом** (`merchantDomainName`), тому правильного ключа замало:
у кабінеті мерчанта має бути заведений `fluent-fox.site`. Інакше шлюз відкине
підпис як чужий, а в `pay-errors.log` буде щось на кшталт
`WayForPay 200: Merchant domain is not allowed`.

MonoPay домену не перевіряє — там автентифікує сам токен.

### Крок 3. Викатка

Секрети підхоплюються на наступному пуші в `master`. Окремо нічого запускати
не треба; щоб не чекати змін у коді, досить перезапустити останній workflow
кнопкою **Re-run all jobs**.

### Крок 4. Перевірка

```bash
# Має бути 200 і JSON із pageUrl — адресою сторінки оплати шлюзу.
curl -s -X POST https://fluent-fox.site/api/pay.php \
     -H 'Content-Type: application/json' \
     --data-raw '{"provider":"mono","amount":1,"description":"test"}'
```

Кирилицю в таку перевірку краще не писати: з Windows-термінала вона поїде в
cp1251, PHP не розбере JSON і відповість `400 Невідомий спосіб оплати` — це
буде помилка команди, а не сайту.

Те саме з `"provider":"wfp"`. Після успішної відповіді відкрийте `pageUrl` і
переконайтесь, що там ваша сума й ваше призначення. Скасовувати рахунок не треба —
несплачений просто протухає (у MonoPay ми ставимо на це годину).

Якщо прийшла помилка, дивіться причину:

```
/home/u260300169/domains/fluent-fox.site/pay-errors.log
```

Відвідувачу текст помилки шлюзу не показується ніколи — він бачить
«Не вдалося створити рахунок. Спробуйте ще раз або напишіть нам».

### Крок 5. Показати кнопку людям

Після того, як обидва шлюзи відповіли `pageUrl`, сторінку треба ще вивести з
тіні — вона навмисно нікуди не прилінкована. Додати `/oplata`:

* у підвал посадкових — `tools/landing/build.py`, список «Розділи»;
* у підвал головної — `tools/home/template.html`, той самий список;
* у підвал блогу — `FOOTER_LINKS` у `tools/blog/build.py` і `blog/index.html`;
* у `sitemap.xml` і `llms.txt`.

Слуг `oplata` у всіх чотирьох правилах `.htaccess` уже є, тож адреса працює
й зараз.

## Чому оплата взагалі йде через сервер

Обидва шлюзи вимагають секрет: WayForPay підписує запит HMAC-MD5 на
`merchantSecretKey`, MonoPay ходить із заголовком `X-Token`. Покласти будь-що
з цього в браузер означає віддати можливість створювати рахунки від імені
школи кожному, хто відкриє «Переглянути код».

Тому `js/pay.js` не знає нічого: він шле суму на свій же `/api/pay.php`, а
назад отримує готову адресу сторінки оплати й переходить на неї. Ні віджета,
ні iframe — через це й CSP у `.htaccess` правити не довелось.

Вебхуків немає навмисно. Вони потрібні тому, хто записує платіж у себе — у
сусідній мережі це робить база на сервері. Тут писати нікуди, а вебхук, який
відповідає не так, як чекає шлюз, змушує його повторювати виклик годинами.
Платіж видно в кабінеті мерчанта, і він приходить листом.

## Якщо міняється версія ассетів

`lead.php` віддає відвідувачу без JS власну сторінку результату й підключає
`style.css` із версією — але тримає її **константою** `ASSET_VERSION`, а не
рядком `?v=…`. 21.09.2026 через це бамп версії пройшов повз нього мовчки:
регулярка `tools/audit/assets.py` шукала саме `?v=`. Тепер аудит дивиться й на
константу, тож розбіжність впаде на `python tools/audit/run.py`.

## PHP локально немає

Синтаксис обох файлів перевіряє крок «Перевірити синтаксис PHP» у
`.github/workflows/deploy.yml` — звичайний `php -l` по всьому `api/`. Він
стоїть **до** rsync, тож зламаний файл на прод не поїде: викатка просто впаде.

Один раз це вже спрацювало. У шапці `pay.php` стояв шлях із глобом
`sites/*/server/wayforpay.js`, а `*/` усередині блочного коментаря закриває
цей коментар — далі файл розбирався як код. Локально це не ловилось нічим.
